# AGENTS.md

Instructions for an AI coding agent working in this repository. Read this first, then [README.md](README.md) for what the product does and [docs/design.md](docs/design.md) for how it is built.

## What this is

Hermes Evals is a local platform that measures whether a change to a [Hermes Agent](https://github.com/NousResearch/hermes-agent) setup (model, skills, memory, tools, MCP servers) makes it better, worse or no different, with a confidence interval. Suites of tasks run under several configurations, each run in its own container with the real Hermes; checks grade the stored evidence; a paired bootstrap over tasks gives the verdict.

Stack: a pnpm + Turborepo monorepo, TypeScript everywhere. NestJS API and worker (`apps/api`), Vue 3 web app (`apps/web`), an egress proxy and model gateway (`apps/egress`), a filtered Docker API (`apps/docker-guard`), shared zod contracts (`packages/shared`). Postgres 17 with pg-boss. Docker Compose runs it all.

## Running it

Needs Docker (Colima or Docker Desktop, Engine 28+ and Compose 2.24+, about 6 GB of memory for the VM) and, for development, Node 22.18+ and pnpm 11.

```bash
docker compose up -d --build   # whole stack: the free mock model (also the LLM judge), the two sample MCP servers, the samples seeded
open http://localhost:8080     # the web app; the API is on :3000
```

No `.env` and no profile are needed. The first build takes 2 to 11 minutes, most of it downloads; a rebuild after a code change about a minute. Then the worker loads the five suites and proves its sandbox, and the api seeds what `samples/` holds and the database lacks (`apps/api/src/samples`): 4 skills, 8 documents, the MCP servers `invoice-db` and `vendor-directory`, and 26 configurations from `samples/configurations.yaml`. Each suite's arms come twice: `<suite>-<arm>-mock` on the mock model, free, and `<suite>-<arm>` on Nous Portal with `openai/gpt-6.1-sol`, which costs money: never launch those unless the user asks (Rules). Experiments › Run a sample experiment launches `invoices-v1-baseline-mock` against `invoices-v1-with-skill-mock` on `invoices-v1`, 48 runs, about 2 minutes, and reads `better`.

To check a stack from a terminal:

```bash
curl -s localhost:3000/api/health           # status ok, database, migrations and queue ok
curl -s localhost:3000/api/system/workers   # one worker online, sandboxProven true
curl -s localhost:3000/api/system/setup     # the judge (mock true by default) and the seed's report: state done, what it created and skipped
```

`.env` is optional and the user's: never edit it (Rules). It holds only what the defaults cannot know: real provider keys, `NOUS_HOST_PROXY`, a real LLM judge (both `JUDGE_PROVIDER` and `JUDGE_MODEL`), or `SEED_SAMPLES=false`; `.env.example` lists every setting. Compose reads each from the shell first, then `.env`. On this kind of machine, if `docker` talks to the wrong daemon, set `DOCKER_CONTEXT=colima` (or `desktop-linux`) for every docker and docker compose command. The development stack may be running the user's experiments: never cancel, pause or delete one you did not start, and before recreating the worker check `slotsInUse` in `/api/system/workers` (a stopped worker hands its running trials back to the queue).

For development outside Docker: `pnpm install`, `pnpm --filter @hermes-evals/shared build` (other packages read its built `dist`), then `pnpm dev`. The API needs a database (`DATABASE_URL`), and its seed `SAMPLES_DIR=../../samples` (it runs from `apps/api`) or `SEED_SAMPLES=false`; a worker started with `pnpm --filter @hermes-evals/api dev:worker` without docker-guard cannot run trials or verifier scripts.

## Checking your work

Run what your change touches, then everything before you call it done:

```bash
pnpm turbo run typecheck lint test build --force    # all packages: types, oxlint/eslint, unit + PGlite integration tests, builds

# Postgres 17 end-to-end tests, against a throwaway server (never the Compose database on :5432)
docker run -d --name hermes-evals-pg-test -e POSTGRES_PASSWORD=test -p 127.0.0.1:55433:5432 postgres:17-alpine -c max_connections=200
TEST_DATABASE_URL=postgres://postgres:test@localhost:55433/postgres pnpm --filter @hermes-evals/api test:e2e

# Real containers (trial image, verifier containers, the fake Nous portal); see docs/phases/phase-1.md 6.1 for the host guard
RUN_SANDBOX_TESTS=1 pnpm --filter @hermes-evals/api exec vitest run <spec>

# On a running stack with the mock model: each phase's smoke prints one PASS/FAIL/SKIP line per step
scripts/phase6b-smoke.sh        # see each script's header for the stack it needs
pnpm exec prettier --check .
```

Each phase document's section 5 lists the exact commands and the counts they gave.

## Rules

These keep the system honest and the user safe. Do not break them, even to make a test pass.

- **Never spend money by accident.** Real model calls cost the user money. Use the mock model for every test and check: provider `custom`, base URL `http://mock-model:8090/v1`, model `mock/scripted`. Run a real model only when the user asks, and say what it will cost first (`config/prices.yaml` holds the prices).
- **Never touch credentials.** Never edit `.env`, never read `~/.hermes`, `auth.json` or the `nous-home` volume, and never start a Nous device login or press Connect in automation. Provider keys live only in `.env` and reach egress, never a trial. MCP secrets are referenced by name; values are never stored, logged or returned.
- **The repository is public.** Never commit a secret, a token or a personal path. Scan before committing.
- **Never point a test at the Compose database** (`localhost:5432`); use PGlite or the throwaway server on 55433. Never delete or prune the stack's Docker volumes: they hold the user's data.
- **The agent under test never sees the answer.** References and checks never enter a trial. Keep it that way in any change to materialisation or the trial spec.
- **Evidence is immutable.** Events, artifacts and finished attempts are never updated or deleted (database triggers enforce it). Re-scoring creates a new evaluation.
- **Suites change through their generators.** Edit `scripts/fixtures/<suite>.ts` and regenerate; `node scripts/fixtures/<suite>.ts --check` must pass. Never hand-edit generated fixtures or references.
- **docker-guard is a security boundary.** Its policy accepts exactly two container shapes. Widen it only on purpose, with tests for every refusal.

## Conventions

- ESM with explicit `.js` suffixes in imports. No `any`. Files under about 400 lines; split before they grow past it.
- A contract change starts in `packages/shared`, then the API, then the web. Rebuild shared after editing it. Every response is parsed with its shared schema in tests.
- Errors are Nest `HttpException`s with `{ statusCode, message, issues? }`. Mutating requests need the `X-Requested-With` header.
- Migrations: change the schema, `pnpm db:generate`, review the SQL, add CHECKs and triggers by hand where the database must enforce a rule, and add an upgrade test like `src/database/phase7-migration.spec.ts`.
- Tests sit beside the code: `*.spec.ts` (unit), `*.integration.spec.ts` (PGlite), `*.e2e-spec.ts` (Postgres 17). A fix comes with a test that fails without it.
- The web app reads the real API in live mode and fixtures in tests; a new page state gets a fixture scenario and a component test.
- Match the surrounding code's comments and naming. Comments say why, in plain sentences.
- Docs are plain English: short sentences, no marketing words, numbers with their units.

## How work is organised

The plan in `IMPLEMENTATION_PLAN.md` section 17 splits the work into phases. Each phase ends with `docs/phases/phase-N.md`, which records what was built, the decisions taken (and their alternatives), the review's findings, how to test it, the known limits, and the open questions with how each was settled (section 6.4). Before changing an area, read the phase document that built it; its decisions are the reasons behind the code.
